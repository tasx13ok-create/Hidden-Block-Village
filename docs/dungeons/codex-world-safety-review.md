# World merge safety review and hardening

Fable supplied the original `tools/world_merge` implementation in `1450679`, with the later doorway and route work integrated from `4f8f25e`. This document records Codex's subsequent review and concrete hardening; it does not claim a recovered world has been pasted or verified in Minecraft. The underlying work remains attributed to Fable.

## Observed defects corrected

1. **Keep-air could delete preserved inventories.** A synthetic existing chest at a schematic-air cell retained block ID 54 with `clear_air=False`, but lost its entire tile entity and pending block tick. Tile/tick replacement now uses the same actual replaced-cell predicate as block writes. Incoming tile tags at skipped-air cells are not inserted over preserved data.
2. **Extended block IDs were absent from height estimates.** An existing block ID 256 at Y=20 has a zero low byte and a nonzero `Add` nibble; the old heightmap could report zero. Occupancy now combines both parts of the ID. This remains a conservative non-air occupancy estimate, not a simulation of modded block light opacity. The receipt says so. Native relighting/height verification remains required.
3. **A marker alone did not establish isolation.** Candidate/source identity is now stored in a schema-2 marker with absolute paths and a candidate ID. Candidate paths, source traversal, region paths, rollback paths and temporary file paths reject symlinks, Windows junctions and all reparse points. Region/rollback names are confined to known dimension paths and validated transaction directories. Copying a marker into the original source does not authorize a paste there. Legacy schema-1 candidates must be copied again. Case-insensitive Windows spellings remain valid.
4. **Late failures could strand an unrecorded partial paste.** All complete region outputs and their exact before snapshots now stage and hash before any candidate region changes. An immutable receipt and a durable pending marker precede publication. A later parse failure changes no regions; a later ordinary publication failure restores the entire pre-command candidate. An interrupted process leaves a pending transaction that can be recovered idempotently.
5. **Rollback could fail halfway or escape recorded paths.** Every selected backup/current-state hash and path validates before any rollback write. Rollback itself is a staged journaled transaction. A late ordinary rollback failure restores its entire pre-command candidate. External/native region edits after a paste are detected and are not silently overwritten. Historical snapshot directories remain retained; retries use fresh transaction identities.
6. **Predictable temporary files could overwrite unrelated paths.** Publication now creates unique files exclusively, flushes/fsyncs their contents and atomically replaces each destination. The old fixed `r.x.z.mca.tmp` name is not touched. An OS-backed candidate lock serializes these tools and is released if a process exits.
7. **NBT was not fully Java-compatible or compression-strict.** The parser/writer now handles Java modified UTF-8 encoded NUL, astral characters represented as surrogate pairs and unpaired UTF-16 surrogates. It rejects malformed sequences and standard four-byte UTF-8 that Java's NBT `readUTF` cannot consume. Gzip/zlib must have complete valid checksums and no trailing data or extra members. Decompressed/input size, nesting and tag allocation are bounded. Valid unknown compound fields and numeric/array tag types, including `TAG_Long_Array`, continue to round-trip.
8. **Malformed/oversized region metadata needed earlier rejection.** Chunk payload lengths include their four-byte prefix in sector bounds; overlapping sector inventories are rejected. Region reads/outputs are bounded at 512 MiB, decoded/edited chunk NBT at 32 MiB, individual paste transactions at 65,536 chunks and 1,024 regions. Unsupported compression/header combinations fail before candidate publication.

## Operating and recovery contract

Use an offline, immutable recovered source or stop the source server before copying. Per-file hash equality proves that each copied file matched its source read; it cannot turn a changing live world into a consistent snapshot. The tools' OS lock coordinates these tools, not Minecraft or external file editors.

`copy_world(source, candidate)` creates a new independent directory and schema-2 marker. `paste_into_world_copy(...)` validates that identity and automatically recovers any incomplete previous command before staging the next one. Before/after files and `PASTE-RECEIPT.json` are retained under `<candidate-name>.rollback/<paste-number>-<transaction-id>/`. Backups are never renamed away during restoration.

`recover_pending(candidate)` can explicitly undo an interrupted command. It validates the entire journal/snapshot inventory and accepts only a region still equal to that command's before or after hash. A second recovery call is a no-op. `rollback(candidate, N)` validates and restores all selected completed pastes; it also handles an interrupted pending operation before acting. An unrelated region edit or damaged snapshot stops recovery before its first write and requires inspection instead of forced overwrite.

Each region replacement is atomic; the operating system does not offer one atomic rename for an entire world. The pending journal provides recoverability across multi-region process interruption. On Windows, Python can fsync file contents but does not expose directory fsync; durability across hardware/filesystem failure therefore still depends on the underlying storage. The path checks and lock target offline operation, not a hostile process racing filesystem replacements between checks.

The marker is provenance/accident prevention, not a cryptographic authorization boundary against someone deliberately forging all metadata. Never run this tooling against live/private originals or replace candidate directories with links to save disk space. Region APIs used by internal fixtures are lower-level than the candidate entry points and do not themselves authorize any live edit.

## Verified scope

Command run from the repository with the prepared Python environment:

```powershell
& '..\.venv\Scripts\python.exe' -m unittest discover -s tests -p test_world_merge.py -v
```

**65 tests passed on Windows**, with no skips in that run: the original 37 tests, Fable's two added doorway tests, and 26 hardening/parser/receipt tests. Coverage includes real Windows junctions, preserved chest inventory/ticks, Add-only block IDs and unknown Forge tags, late parse/publication failures, durable process-interruption recovery, rollback failure and damaged backups and missing staged outputs with intact before snapshots, source/path isolation, concurrent-operation lock, unique temporary files, case-insensitive path identity, Java UTF golden bytes and strict compressed stream rejection. All world mutations in those tests use disposable synthetic fixtures. No real recovered world or supplied schematic was edited.

The five supplied v17 static audits are separate evidence. A reported Nether ladder at local `132,95,144` faces an open trapdoor at `132,95,145`, with ladder segments above and below. Treat this as a native verification candidate; do not automatically fill or delete it based solely on the support heuristic. Doorway proposals likewise remain proposals until the reviewed source hash and explicit edits are accepted. This safety pass does not authorize schematic modifications or a real world paste.

Remaining verification: native load/lighting/fluid/tile behavior in an approved copy, full-assembly registry mapping, and human traversal/visual review. `paste-world` now validates its external `--receipt` before calling the mutation API: existing paths, links/reparse points and paths inside source/candidate/rollback directories are refused, and a writable output descriptor is reserved with exclusive creation. Seven CLI regressions verify that invalid outputs leave the complete candidate inventory/bytes unchanged, source bytes unchanged and the mutation API uncalled; successful synthetic paste writes its external receipt. If a later output-device failure occurs after commit despite preflight, the CLI explicitly says the paste committed and points to the independent internal receipt. Failed commands remove only their own reserved output file.
